# Blackbox 加载性能排查（2026-09-16）

## 结论与范围

本次诊断用户实际访问的 `http://127.0.0.1:8013`，没有修改业务代码、重启服务或修改生产数据库。

8013 是现有 SSH 本地转发，目标为远程 `127.0.0.1:8010`，不是 Windows 本机后端。远程仓库 `/home/userjd/.agents/blackbox` 的 HEAD 为 `def38a2`，但 `main.py` 另有未提交修改（52 行新增、1 行删除），并存在本地部署配置及测试。后续实施不能直接覆盖这些修改。

主要问题是：较慢的实际传输链路上反复发送大型、未压缩的总览；所有页面首屏依赖总览；地图详情又包含昂贵的证据计算和重复数据。之前的优化减少了内存占用和地图目录计算，没有消除这些瓶颈。

## 实际 HTTP 测量

以下是运行中的真实服务测量，不是合成数据库测试。请求顺序执行，未进行并发压测。测量期间服务负载可能变化。

| 请求 | 服务器本机总耗时 | 经 8013 的耗时 | 响应字节数 |
|---|---:|---:|---:|
| 页面 HTML | 0.005 秒 | 0.373 秒 | 980 |
| 总览 dashboard | 1.682 / 1.781 / 1.818 秒 | 45.012 秒；首字节 1.869 秒 | 2,938,177 |
| 地图目录（不含证据） | 0.015–0.018 秒 | 0.182 秒 | 4,936 |
| 一张地图详情 | 2.343 / 2.394 秒 | 未测完整传输 | 971,540 |
| ECharts JS | 0.007 秒 | 13.386 秒；首字节 0.057 秒 | 1,060,975 |

另一次总览请求首字节为 4.626 秒，40 秒超时前仅收到 2,621,440 字节。完整请求平均吞吐约 65 KB/s，ECharts 请求约 79 KB/s。这证明传输阶段是当前明显瓶颈，但不足以判定是 SSH 参数、底层网络还是其他传输竞争造成；本次没有更改隧道。

客户端发送 `Accept-Encoding: gzip` 后响应仍无 `Content-Encoding`。服务器本机离线压缩结果：

| 内容 | 原始字节 | gzip 字节 | 缩减 |
|---|---:|---:|---:|
| 总览 | 2,938,177 | 497,625 | 83.1% |
| 地图详情 | 971,540 | 152,999 | 84.3% |
| 首屏 JS + CSS 合计 | 2,256,376 | 689,113 | 69.5% |

这些是压缩潜力测量，不是已部署后的加速结果。静态资源已有 ETag / Last-Modified，但未返回明确的 Cache-Control；ECharts 被 HTML modulepreload 首屏加载。

## 总览响应与计算

总览即使只返回最近 200 个 Run，仍返回全量项目、研究、分支集合，并扫描候选 Run 选研究代表。

响应组成：产物 980,911 字节（其中 preview_json 838,375）；研究 838,764 字节（其中 champion_run 690,671）；分支 597,361 字节；最近 Run 361,047 字节（其中 config_json 134,478）；笔记 132,073 字节。很多字段对导航和初次进入当前页面没有必要。

只读 SQLite 连接的 cProfile 诊断显示：

- 总览组装执行 32 次 SQL。
- 代表 Run 选择是主要计算热点，仍遍历候选，逐条调用 choose_representative；之前按批读取仅降低内存。
- 每个研究又扫描完整 branches 列表，形成研究数 × 分支数的 Python 属性访问和过滤。
- `ORDER BY runs.updated_at DESC LIMIT 200` 查询计划为 `SCAN runs` + `USE TEMP B-TREE FOR ORDER BY`，缺少支持这个排序的索引。
- 活动历史已有汇总表，但判断缓存有效性仍要检查全量 Run 变更；失效时重建汇总，不应把它描述为每次都完全重算。

诊断中的总览 cProfile 总时长 8.483 秒，仅用于定位函数热点；它包含明显分析器开销，不能替代上表 1.7–1.8 秒的实际 HTTP 耗时。SQL execute 计时不包含全部结果抓取、ORM 转换和 Python 处理时间。

参考：`apps/server/blackbox_server/main.py` 的 dashboard、dashboard_champion_runs_by_research、ensure_run_activity_daily_cache；`representatives.py` 的 representative_rows。

## 地图详情

只读函数分析的一次地图详情组装触发 3,854 次 SQL、221 次完整 Run 质量检查和 460 次曲线数据读取/解析调用。主要路径：

`map_detail → node_read → resolve_binding → run_evidence → run_quality_gate_report → run_detail / validate_run_detail`

质量检查会组装 Run 详情、读取曲线文件并重新计算校验。已有单次请求缓存能避免相同 Run 在一次请求中重复校验，但下一次轮询会重新执行。

此处 cProfile 总时长为 32.076 秒，属于带分析器的新进程测量，不能声称线上地图请求需要 32 秒；实际运行服务该地图为约 2.4 秒。

响应中 `nodes` 为 482,326 字节，`tree` 为 485,882 字节，几乎把完整节点复制了两遍。当前 WebUI 由 nodes 建立关系，没有读取 map.tree。

## 前端放大机制

`webui/src/App.jsx`：

- 页面渲染在 data 缺失时被总览请求阻塞，直接打开地图也需要先等总览。
- setInterval 每 15 秒调用 refresh；WebSocket 事件另外以 250 ms 防抖触发同一个完整 refresh。
- 没有统一的请求进行中合并、过期结果保护、后台标签页暂停机制。
- 经 8013 一次总览下载约 45 秒，已经超过三个刷新间隔，存在请求重叠和争抢带宽的条件；未通过浏览器瀑布图统计具体重叠数量。
- 每次 setData 都替换对象，地图 hook 的 refreshToken=data 随之变化，又请求完整地图详情。
- 当前保留旧地图与缩放状态的处理修复了交互闪烁，但没有减少网络或后端计算。

## 建议实施顺序

### 第一批：尽快降低首屏和刷新成本

1. 在实际经过的 8010 服务层启用 HTTP gzip，或让现有转发路径经过提供压缩的代理。只改一个没有经过的外层代理不会生效。哈希静态文件配置长期缓存，HTML 单独使用可更新的缓存策略。以响应头、真实传输字节及旧版本切换验证。
2. 给 refresh 加单请求合并和尾随刷新，定时器等待上次完成；页面不可见时暂停常规轮询；WebSocket 按对象/页面更新对应数据。避免旧请求覆盖新状态，保留失败重试。
3. 增加 WebUI 专用轻量导航/总览接口，保留现有 API 默认行为以兼容 CLI/SDK。首屏只要导航标识、计数、代表的关键指标；产物 preview、完整配置、笔记正文、完整研究/分支详情按需加载。页面不再依赖整个 dashboard 才能开始请求自己的数据。

压缩可以先减少传输，但以本次吞吐估算，0.50 MB 仍需数秒；仅开启压缩不足以完成优化。

### 第二批：降低后台 CPU 和地图详情成本

4. 研究/分支先按 ID 一次分组，避免每个研究重复扫描全部分支；为常用时间排序补迁移索引并验证查询计划。代表 Run 使用增量结果或带版本的缓存，按 Run 指标/状态、归属、基准和地图状态变化失效。严格保留人工基准 → 最高有效指标 → 最新的用户规则，并保留远程已有业务特例。
5. 地图首屏仅返回扁平 nodes 与必要展示证据；tree 做可选返回，保持旧调用兼容。选中节点再加载详细证据/笔记。
6. 质量结果按 Run 与产物版本复用，将重复曲线校验移出地图读取热路径；状态和产物变更要失效，未知/待检查不能误报通过。提交、结束、比较等原有强制质量门继续生效。节点、Run、产物、笔记的元数据批量查询，消除大量逐节点 SQL。
7. 地图使用自身变更版本刷新，不因无关总览更新而重取；版本应涵盖绑定 Run、基准及质量依赖，不能只检查地图自身 updated_at。

### 第三批：首屏资源与链路

8. 路由/图表按需拆包，取消非图表页面对完整 ECharts 的提前依赖；评估按图表类型引入模块。继续沿用已有 UI 和图表库。
9. 比较用户已授权的其他现有访问路径、隧道竞争和下载吞吐，定位 65–79 KB/s 的原因。不需要为诊断新增公网暴露。

## 验收与边界

- 固定同一数据和页面，对比首次与二次进入、总览、地图、Run 详情；记录 TTFB、完整下载、响应字节与页面可交互时间。前端可交互时间本次未测。
- 建议首批目标：常用首屏业务 JSON 压缩后不超过 100–200 KB；无变更刷新不发送完整对象；同一资源最多一个进行中请求。具体耗时目标需基于改造后的实测确定。
- 检查隐藏标签、慢网络、事件密集写入和切页；验证选中项、缩放平移、状态切换、代表选择与质量门不回退。
- 测量时远程有 224 个逻辑 CPU；短时 vmstat 显示 CPU 空闲 98–99%、IO wait 0%。不能仅凭 load average 较高认定机器 CPU/磁盘饱和，也未排除其他时段竞争。
- 本次未运行全套测试，因为没有修改业务代码；没有执行部署、索引迁移、缓存改造或生产数据库写入。
- 一次包含业务统计输出的诊断脚本被自动审批拒绝，未执行。随后获准的脚本只输出性能元数据，数据库分析强制 mode=ro。
