# 总体架构

## 1. 总体架构

建议采用如下架构：

```text
          ┌────────────┐
          │   Web UI   │
          └─────┬──────┘
                │ HTTP / WS
┌────────────┐  │
│    CLI     │──┼──────────────┐
└────────────┘  │              │
                ▼              ▼
          ┌────────────────────────┐
          │   FastAPI Application  │
          │  - REST API            │
          │  - WebSocket           │
          │  - Static WebUI Serve  │
          │  - Auth                │
          │  - Search/Compare      │
          └─────┬──────────┬───────┘
                │          │
                ▼          ▼
        ┌────────────┐  ┌──────────────┐
        │ PostgreSQL │  │ Object Store │
        │ Metadata   │  │ S3 / MinIO   │
        └────────────┘  └──────────────┘
                │
                ▼
          ┌────────────┐
          │ Queue      │
          │ optional   │
          └─────┬──────┘
                ▼
          ┌────────────┐
          │  Workers   │
          │ Preview    │
          │ Extractors │
          │ Compare    │
          └────────────┘
```

## 2. 组件职责

### 2.1 FastAPI 服务

负责：

- 提供 REST API
- 提供 WebSocket 实时更新
- 作为 WebUI 的 HTTP 服务器
- 认证与鉴权
- 资源生命周期管理
- 查询、比较、lineage 聚合
- Artifact 上传协商

### 2.2 WebUI

负责：

- 浏览项目、Research、分支、运行
- 查看指标、曲线、产物
- 比较多个 run
- 查看分支 lineage
- 搜索、筛选、保存视图

### 2.3 CLI

负责：

- 给 AI Agent 和自动化脚本提供稳定入口
- 全量覆盖常用后端能力
- 统一 JSON 输出
- 支持离线写入/同步
- 支持脚本式编排

### 2.4 SDK

负责：

- 代码中低摩擦记录实验
- 自动采集上下文
- 批量写入
- 异常重试
- 大文件上传与 artifact 注册

### 2.5 Worker

负责异步任务：

- 文件预览生成
- 表格 profile 提取
- 报告摘要抽取
- 对比缓存构建
- sweep 统计
- 大型 artifact hash / dedup

## 3. 存储职责拆分

### 3.1 PostgreSQL

适合存：

- Project / Research / Branch / Run 元数据
- Event
- 小规模 scalar metrics
- 可检索 summary
- tags / notes / snapshots
- 查询索引

### 3.2 Object Store（S3 / MinIO）

适合存：

- 回测报告
- HTML / PNG / PDF
- 大 DataFrame
- 日频/分钟级曲线原始数据
- 持仓、交易流水
- Notebook
- 代码 patch 文件

### 3.3 Queue / Worker

V1 使用轻量内置 worker。后续团队部署可接 Redis + ARQ/RQ/Celery，用于：

- 异步任务队列
- 实时事件 fan-out
- 临时 compare cache
- rate limit / session cache

## 4. 两种部署模式

### 4.1 本地单机模式

适合个人研究员或初期开发：

- FastAPI
- SQLite
- 本地文件系统
- 可不启 Worker
- WebUI 直接由 FastAPI 提供

优点是轻，缺点是后期扩展有限。

### 4.2 团队服务模式

适合研究组或公司内部部署：

- FastAPI
- PostgreSQL
- MinIO/S3
- Redis
- Worker

本地单机模式是 V1 默认路径；团队服务模式在同一 API 和存储适配层上平滑扩展。

## 5. 写入路径

### SDK/CLI 写入流程

1. 创建或获取 Run
2. 发送 event / metric / note
3. 若有大产物，先请求上传凭证
4. 上传文件到对象存储
5. 回调服务器完成 artifact 注册
6. Worker 异步生成预览与摘要
7. WebUI 实时刷新

## 6. 读取路径

### WebUI / CLI 查询流程

1. 查询 Project / Research / Branch / Run 基本信息
2. 读取 summary metrics 和 events
3. 按需拉取 artifact 预览
4. 需要下载明细时再取对象存储文件
5. Compare 页面使用预计算摘要，避免每次全量加载

## 7. 关键设计决策

### 7.1 “元数据入库，大产物入对象存储”

这是必须的。  
量化回测的许多产物可能很大，尤其是：

- 分钟级收益序列
- 全市场因子暴露矩阵
- 持仓与交易流水
- 参数搜索全量结果

不应全部塞进关系库。

### 7.2 “Run summary” 单独冗余存储

为了让搜索和列表页快，建议每个 Run 都维护一份 summary：

- 关键指标
- 关键配置摘要
- 关键标签
- 状态
- 时间
- 最重要的 artifact 引用

列表、搜索、排序都靠它。

### 7.3 UI 只看抽样和摘要，原始数据按需下载

例如：

- 权益曲线：DB 中只保存 preview points 或统计摘要
- 全量日收益：保存在 parquet artifact
- WebUI 显示抽样线 + 下载原始文件入口
