# 实施建议与仓库结构

## 1. 推荐技术选型

在 Python + FastAPI 前提下，建议：

### 后端
- FastAPI
- Pydantic v2
- SQLAlchemy 2.x
- 内置 schema migration
- SQLite 本地模式，PostgreSQL 团队模式
- 本地文件存储，MinIO/S3 团队模式
- 轻量内置 worker，后续再接 ARQ / RQ / Celery

### CLI
- argparse
- 默认结构化 JSON 输出，Agent 模式优先稳定可解析

### SDK
- requests / httpx
- pandas / pyarrow 集成
- 本地 spool 与 retry 机制

### WebUI
- 前端技术可独立，但最终静态资源由 FastAPI 托管
- V1 重点是信息架构，不是复杂交互

## 2. 推荐仓库结构

```text
blackbox/
├── apps/
│   └── server/
├── packages/
│   ├── sdk/
│   ├── cli/
│   └── common/
├── webui/
├── docs/
├── scripts/
└── tests/
```

其中：

- `common`：放共享 schema、枚举、类型定义
- `sdk`：轻客户端
- `cli`：面向 Agent 的命令封装
- `server`：FastAPI 服务
- `webui`：独立前端工程，构建后由 server 提供静态资源

## 3. 建议开发阶段

### Phase 1：最小闭环
目标：先把“能记录、能看、能比”跑通。

包含：

- Project / Research / Branch / Run 模型
- SDK `init/log/artifact/finish`
- CLI `run start/log/upload/finish/search`
- WebUI：
- Project 列表
  - Research 页面
  - Run 页面
- SQLite + 本地 artifact 存储默认可用，Postgres + MinIO/S3 作为团队部署扩展

### Phase 2：分支与比较增强
包含：

- Branch lineage 图
- Compare 页面
- config diff
- notes / decision records
- sweep 模型

### Phase 3：量化专用能力
包含：

- 因子/策略内置 helper
- 标准回测报告抽取器
- 风险、成本、IC 预览模板
- 参数热力图
- champion run 推荐

### Phase 4：Agent 优化
包含：

- 更完整的 JSON 输出
- 资源选择器
- 批量命令
- sync / offline mode
- 更细粒度搜索 DSL

## 4. 测试策略

### 单元测试
覆盖：

- schema 校验
- run 状态机
- lineage 构建
- compare 汇总
- artifact 注册逻辑

### 集成测试
覆盖：

- SDK -> API -> DB -> Object Store
- CLI -> API
- 上传流程
- worker 预览生成

### 端到端测试
模拟：

- 新建 research -> 新建 branch -> 启动 run -> 写 metric -> 上传 artifact -> compare

## 5. 最重要的产品取舍

如果只能先做好几件事，优先级建议如下：

1. **Research / Branch / Run 模型**
2. **Run summary + artifact 管理**
3. **Compare 能力**
4. **Lineage 展示**
5. **Agent 友好的 CLI**

因为这五项，正好覆盖了你的真实研究场景。
