# 领域模型

## 1. 核心对象

建议采用以下对象模型：

| 对象 | 含义 | 作用 |
|---|---|---|
| Workspace | 工作空间 | 团队或实例级隔离 |
| Project | 项目 | 一个策略族、研究方向或产品线 |
| Research | 研究对象 | 一个相对明确的问题域，如“中证500反转因子” |
| Branch | 研究分支 | 一个连续演化的思路分支 |
| Run | 一次运行 | 一次具体执行，通常对应一次回测/评估 |
| Event | 事件 | 关键阶段日志 |
| Metric | 指标 | 标量或小型序列 |
| Artifact | 产物 | 报告、表格、图片、Parquet、Notebook 等 |
| Snapshot | 快照 | 代码、数据、环境、配置快照 |
| Note | 备注/决策记录 | 人或 Agent 写下的原因与结论 |
| Sweep | 参数搜索集合 | 一组有共同搜索空间的 Run |
| CompareSet | 对比集合 | 一组供 UI/CLI 快速比较的 Run 集合 |

## 2. 推荐层级关系

```text
Workspace
└── Project
    └── Research
        ├── Branch A
        │   ├── Run 1
        │   ├── Run 2
        │   └── Run 3
        ├── Branch B
        │   ├── Run 4
        │   └── Run 5
        └── Sweep X
            ├── Run 6
            ├── Run 7
            └── Run 8
```

## 3. 为什么要显式引入 Branch

很多实验系统只有 Run，没有 Branch。  
但你的场景里，**分支是核心语义**：

- “从 baseline 复制出来，改了手续费模型”
- “突然想到把行业中性化换成 Barra 暴露回归”
- “实现方式从 pandas 切到 numba”
- “参数扫描后挑出两个候选，再继续深挖”

如果不显式建模 Branch，后面就只能在 tags 或 notes 里找上下文，无法自然呈现研究脉络。

### Branch 建议字段

- `id`
- `research_id`
- `name`
- `title`
- `parent_branch_id`：允许分支树
- `source_run_id`：从哪个 run 演化而来
- `reason_code`：分支原因
- `reason_summary`
- `hypothesis`
- `expected_change`
- `status`：active / paused / accepted / rejected / archived
- `created_by`：human / agent / system

## 4. Run 的语义

Run 表示一次具体执行，应该尽量 **不可变**。

一个 Run 通常绑定：

- 某个 Branch
- 一套 config
- 一份代码快照
- 一份数据快照
- 一份环境快照
- 一组 metrics
- 一组 artifacts
- 一串 events

Run 结束后，允许追加：

- Note
- Tag
- 人工评语
- 结果判定

但不建议允许随意修改原始指标和产物引用。

## 5. 事件模型

量化研究中，日志的关键不是“第 17 步”，而是“哪个阶段”。

因此 Event 建议采用 append-only 模型，至少包含：

- `run_started`
- `data_loaded`
- `factor_generated`
- `neutralization_done`
- `pre_cost_backtest_done`
- `post_cost_backtest_done`
- `risk_analysis_done`
- `artifact_uploaded`
- `run_finished`
- `run_failed`

每个事件都有：

- `event_type`
- `stage`
- `timestamp`
- `payload`
- `sequence_no`

这样 WebUI 可以自然展示 timeline，CLI/Agent 也更容易解析。

## 6. 指标模型：不要只支持 `step=int`

建议 `MetricPoint` 支持 4 类记录坐标：

### 6.1 Event Axis
适合阶段性指标。

例子：

- `strategy.summary.sharpe @ event=post_cost_backtest_done`
- `factor.summary.ic_mean @ event=factor_eval_done`

### 6.2 Iteration Axis
适合参数遍历或手工迭代。

例子：

- `score @ step=12`
- `ir @ sweep_iter=34`

### 6.3 Time Axis
适合真正的时序数据。

例子：

- 日收益曲线
- 日净值曲线
- 日 IC 曲线

### 6.4 Coordinate Axis
适合参数网格。

例子：

- `lookback=20, hold=5`
- `delay=1, neutralize=industry`

这比单纯的 `step=1,2,3...` 更适合量化研究。

## 7. 指标命名空间建议

建议统一使用 namespace，避免后期混乱。

### 策略类

- `strategy.summary`
- `strategy.returns`
- `strategy.drawdown`
- `strategy.positions`
- `strategy.trades`

### 因子类

- `factor.summary`
- `factor.ic`
- `factor.rank_ic`
- `factor.quantile_returns`
- `factor.turnover`
- `factor.coverage`

### 风险与成本

- `risk.exposure`
- `risk.factor_exposure`
- `risk.style_exposure`
- `cost.summary`
- `cost.breakdown`

### 流水线与系统

- `pipeline.stage`
- `system.runtime`
- `system.resource_usage`

## 8. Artifact 类型建议

建议对 Artifact 进行类型化，而不是只存文件。

### 常见类型

- `report_html`
- `image_png`
- `chart_json`
- `table_parquet`
- `table_csv`
- `notebook_ipynb`
- `config_yaml`
- `returns_series_parquet`
- `trade_log_parquet`
- `position_log_parquet`
- `factor_values_parquet`
- `risk_report_json`
- `code_patch_txt`

类型化的意义在于：

- UI 知道如何预览
- API 知道如何索引
- Compare 页面知道如何抽取摘要
- Agent 知道该下载什么

## 9. Snapshot 设计

每个 Run 最少应有 4 类快照：

- **Config Snapshot**：参数、开关、执行选项
- **Code Snapshot**：git commit、是否 dirty、patch、repo URL
- **Data Snapshot**：数据集名、版本、时间范围、指纹
- **Env Snapshot**：Python 版本、依赖、容器镜像、OS、机器名

对于量化研究，Data Snapshot 里建议额外记录：

- universe 定义
- benchmark
- 交易日历
- 复权方式
- 是否含未来函数保护
- 是否生存者偏差处理
- 费用模型
- 滑点模型
- 撮合假设

## 10. Note / Decision Record

这是很多系统缺失但实际极有价值的一层。

每条 Note 可以有：

- `kind`: hypothesis / observation / anomaly / decision / todo / review
- `summary`
- `content_md`
- `structured_fields`
- `author_type`: human / agent / system

示例：

```json
{
  "kind": "decision",
  "summary": "从行业哑变量中性化切换到Barra风格暴露回归",
  "structured_fields": {
    "change_dimensions": ["neutralization_method"],
    "expected_effect": {
      "rank_ic_mean": "up",
      "coverage": "down"
    }
  }
}
```

这对后续 Agent 自动追踪“为什么会有这个分支”非常有帮助。
