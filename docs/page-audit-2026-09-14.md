## 3. 总体判断

现有表格、配置差异、曲线、树和时间线的技术方向是正确的。主要问题是：同一页面有多个争夺首屏的任务；查询范围与上下文不清；“最优候选”“可决策”等词比证据支持的程度更强；通用的元数据/操作面板与研究判断混在同一阅读顺序中。

建议确定以下信息的权威位置：

| 信息 | 权威位置 | 其他页面的表达 |
|---|---|---|
| 项目下研究对象的集合 | 项目页的研究线表 | 总览仅给最近/需关注摘要，侧栏仅导航 |
| 一条研究线的目标、当前结论与待评审对象 | 研究线页 | 总览给待办入口，项目页给短摘要 |
| 某思路的 Run 演进与配置变化 | 分支页 | 研究线给代表摘要与入口 |
| 单次运行的结果、原始证据、配置和运行状态 | Run 详情 | 别处引用摘要，点击回到该 Run |
| 多 Run 指标和配置的字段比较 | 对比详情 | 项目/分支保留快捷比较摘要，不复制完整工作台 |
| agent 编写的命题、去向、阶段和基准路径 | 研究地图 | 内嵌视图复用同一地图，不能重新推导一套“结论” |
| 研究资产规模与陈旧状态 | 研究资产管理 | 总览只露出可进入处理的异常摘要 |

指南依据：§1.1、§2.2–2.5、§3.1、§4.8。尤其要区分三种关系：Project→Research→Branch 的归属，Branch/Run 的自动血缘，研究地图的人工叙事。它们不能合并为一棵含义不明的树。

## 4. 逐页信息模型与建议

### 4.1 总览 `/`

- **主信息**：近期研究进展、运行异常、需要评审的对象；主模型为概览与待办队列。
- **关联信息**：所属项目/研究线、时间范围、最近结果、系统健康。
- **用户动作**：识别异常或待评审项，进入对应研究线/Run；恢复最近工作。
- **当前骨架**：9 项统计 → 完整项目表 → 年度活动热图 → 最近结果/活跃研究/质量收件箱/候选 → 折叠系统概览。概览骨架适合，但顺序不适合“先发现待办”。
- **具体问题**：现场 22 项项目表占满首屏，质量收件箱和候选在后面；没有页面 h1；工作区/搜索视图等总量与运行异常同等突出；候选按 Sharpe 排序，不等于正式研究结论。
- **建议结构**：标题与观察范围 → 运行中/失败/待评审等少量摘要 → 待处理队列与最近结果 → 活跃研究 → 活动趋势；项目目录和系统详情保留为次级区域/入口。待办仅使用已有规则，不新增研究判断算法。
- **依据/代码**：指南 §2.1、§3.1–3.3、§4.7；`App.jsx:632` Dashboard、`App.jsx:778` 附近候选与质量规则。截图 `01-dashboard-before.png`。

### 4.2 项目 `/projects/:id`

- **主信息**：项目范围内各研究线的进展和差异；主模型为有明确项目范围的集合。
- **关联信息**：项目说明、地图、保存的对比集/搜索视图、最近 Run、保留策略。
- **用户动作**：定位研究线、比较项目内候选、打开地图或保存视图、编辑项目。
- **当前骨架**：项目详情 + 统计 + 元数据 + 活动表 + 快捷对比 + 研究线表 + 其他列表。集合骨架合适，重复较多。
- **具体问题**：标题说明与元数据重复；低频 Retention Policy 在研究列表之前；同一批研究线出现在活动表、快捷比较、研究线表三个位置；大量缺失 Sharpe 的诊断研究也被叫作“最优候选”。
- **建议结构**：项目标题/状态/编辑入口 → 项目范围研究线表（目标、状态、最近进展、Run 数、代表证据）→ 已选研究线的快捷比较；“地图与保存视图”“项目设置”作为清楚的次级区域。保留既有比较能力与选择策略，先把选择依据标明。
- **依据/代码**：§2.3 集合、§3.1 权威位置、§3.6 重复、§4.2；`App.jsx:1964` ProjectPage。截图 `02-project-before.png`。

### 4.3 研究线 `/researches/:id`

- **主信息**：研究目标、当前结论、分支进展和下一次评审；主模型为研究对象的判断工作区。
- **关联信息**：地图叙事、自动血缘、候选 Run、评审 note、对比集、历史活动。
- **用户动作**：理解正在验证的命题，查看证据，比较候选，进入分支，执行已有状态/元数据操作。
- **当前骨架**：摘要 → 560px 内嵌地图 → 完整评审板 → 分支表 → 最近 Run → 对比集 → 快捷对比 → 折叠血缘/活动。每个模块都合理，但组合后主任务不明确。
- **具体问题**：有图时评审任务被推后，无图时仍留实现说明；评审板里的 `save_candidate_compare_set` 直接暴露 API 动作编码；`Next` 被翻译成“下一页”；active/Research Review/Candidate Set 等中英混杂。地图和自动血缘缺少就近的语义区分。
- **建议结构**：对象头（目标、当前研究状态、基准/候选依据）→ 需要处理的评审项 → 单层同对象视图“研究脉络 / 分支与 Run / 评审记录”。地图保留在研究脉络，有地图时作为主表达；血缘另标“实验来源关系”；不把编辑表单塞进血缘折叠区。
- **依据/代码**：§2.2、§2.5、§3.1–3.2、§4.5–4.6；`App.jsx:2718` ResearchPage、`2871` ResearchReviewPanel。截图 `03-research-before.png`。
- **待确认**：研究线默认首先看地图，还是首先处理评审？建议默认“结论/待评审摘要 + 研究脉络”，并记住用户切换的视图。

### 4.4 分支 `/branches/:id`

- **主信息**：同一思路上的 Run 序列、相邻版本改变了什么；主模型为演进与差异。
- **关联信息**：分支假设、来源 Run、状态、代表 Run、曲线与决策记录。
- **用户动作**：比较当前和上一 Run、追溯改动、打开证据、维护既有分支状态。
- **当前骨架**：摘要 → Run 表与最佳候选 → 快捷对比 → 折叠上下文（编辑、血缘、指标演进、配置演进）。列表适合，但核心“演进”藏在上下文里。
- **具体问题**：Run 表重复本页固定的 Branch 列；配置变化与指标变化不在同一视野；自动按 Sharpe 找 best，与归档说明、最新跟踪等业务意义可能不一致。
- **建议结构**：分支身份/假设/状态与来源 → Run 序列表（新增就近的配置差异摘要，复用已有 diff）→ 选择两次运行的配置/指标并排对照与曲线；血缘作为来源辅助，元数据编辑作为次要操作。
- **依据/代码**：§2.4 diff、§3.1 变化、§4.2、§4.8；`App.jsx:3278` BranchPage、`BranchConfigEvolution`。截图 `04-branch-before.png`。

### 4.5 Run 集合 `/runs`

- **主信息**：同一查询范围内多次运行的差异；主模型为二维比较表。
- **关联信息**：项目/研究线归属、状态、作者、关键指标、产物与配置摘要。
- **用户动作**：筛选、排序、分页、选择 Run、创建已有的对比集、打开详情。
- **当前骨架**：标题 → 统计 → 查询表单 → 13 列表格 → 分页。骨架正确。
- **具体问题**：源码请求 `{limit:1000,max_scan:5000}` 后再本地筛选和分页，现场系统总数 12,840、表里 1000，却叫“全部 Run”；筛选为失败得到 40/1000，URL 仍 `/runs`，刷新变回 1000/1000；1024px 时表格实测 1810px，容器 711px，右侧字段需要长距离横滚，查询栏也被裁切。长期 ID、完整配置、创建/更新时间同时占列。
- **建议结构**：标题旁明示查询范围 → 高频筛选（关键词/项目/状态）+ 可展开高级条件 + 始终可见的已用条件 → 表格默认身份/状态/关键结果/证据/更新时间 → 选中后出现比较操作条 → 分页和范围说明。低频列由列设置/展开行提供，保持字段比较仍可横向进行。
- **边界**：第一阶段明确“已加载 1000 条中的结果”，保留现有请求契约。真正全量服务端分页/排序另列 API 能力项，不用静默扩大扫描或伪造总页数解决。
- **依据/代码**：§3.3、§3.5、§4.2；`App.jsx:2225–2500` RunsBoardPage、`11220` 附近路由。截图 `05`、`13`、`14`。

### 4.6 Run 详情 `/runs/:id`

- **主信息**：该运行的结果和证据；运行中/失败时为进度、失败阶段及原因。仍围绕同一个 Run，不做新业务对象。
- **关联信息**：来源、研究归属、配置 diff、code/data/env、产物、事件、note。
- **用户动作**：判断结果、查看/下载证据、核对配置、克隆、追加记录、执行已允许的 finish/fail/cancel。
- **当前骨架**：对象头 → 归属/时间摘要 → 结果覆盖摘要 → 诊断 → 7 个 Tab → 折叠 Actions。详情骨架合理。
- **具体问题**：长 ID/归属/时间在说明与摘要重复；“HEALTHY / Key Metrics 3/7”主要描述证据可读性，容易被理解为研究通过；现场一些结果字段为 `--`，对比矩阵却有值，需核对 namespace/模板契约，不能直接推断真实指标缺失。动作埋在页尾；普通 button 实现 Tab，未提供完整 tab 语义；Config 视图调用 `configSummary`（`App.jsx:10876`），只传入配置前三项的逗号串，该字段的“展开”并不能恢复剩余配置项。
- **建议结构**：精简对象头 + 当前状态/原因/适用动作 → 结果指标和主图（运行中/失败优先执行事件与原因）→ 单层“结果 / 过程 / 证据 / 配置与来源 / 笔记”；字段与现有功能全部保留。完整配置用可搜索的分组字段或可展开 JSON；source diff 继续直接对照。状态操作就近展示对象和后果，不改服务端状态机。
- **依据/代码**：§3.1–3.2、§4.4、§4.6、§4.8、§4.11；`App.jsx:4357`、`5124`、`5207`、`5399`。截图 `11`、`12`。

### 4.7 对比列表 `/compare`

- **主信息**：保存的比较方案/比较范围；主模型为可重入的集合目录。
- **关联信息**：项目、研究线、比较 Run 数、模板、创建时间。
- **用户动作**：找到/打开已有对比，开始临时对比并保存。
- **当前骨架**：统计 + 筛选表格 + 折叠临时对比。目录表合适。
- **具体问题**：临时对比入口藏在底部；表里以多个内部 Run ID 作为说明，辨识价值低；项目字段出现在前，真正要打开的 Compare Set 位于第三列；列表为空与筛选无匹配共用“暂无保存的对比集合”提示。现场列表为全部项目，面包屑却残留先前项目。
- **建议结构**：“对比集”标题 + “新建对比”入口 → 范围筛选 → 对比名称优先的表（所属范围、比较意图/阶段、Run 数、更新时间）；临时对比进入明确工作区，保留原保存接口。
- **依据/代码**：§2.3 集合目录、§3.5、§4.2；`App.jsx:6714` CompareWorkbenchPage。截图 `06-compare-list-before.png`。

### 4.8 对比详情 `/compare/:id`

- **主信息**：同一比较范围内方案的字段差异与权衡；主模型为比较/差异。
- **关联信息**：基准选择、样本时段、指标方向和单位、配置差异、曲线、质量诊断与产物。
- **用户动作**：明确比较范围和基准，比较字段、查看差异和证据，保留研究结论。
- **当前骨架**：比较摘要 → 诊断 → 曲线/回撤 → 指标矩阵 → 配置差异 → 原始 Run 等。**这是本项目较适合任务的骨架，应保留。**
- **具体问题**：`runs.length >= 2` 且无请求错误就显示绿色“可决策”（`App.jsx:6856`），与成本/OOS/诊断是否通过无关；现场同时出现“可决策”和 `1 WARNING`。基准、领先候选、主指标被挤在 8 列小格里，必须多次展开；默认基准来自选择顺序，主指标来自有值字段顺序，需明示依据。配置差异和可比性上下文远离结论，原始字段路径/单位不够易懂。
- **建议结构**：比较对象、基准和范围条 → 可比性信息/缺失提示 → 精简差异摘要 → 指标矩阵与配置差异（就近切换，保留列对应）→ 曲线和证据 → 保存/记录入口。把“可决策”改为仅陈述技术事实的“已生成对比”，研究评审去向引用已有正式记录。诊断若影响解释，摘要中直接说明。
- **边界**：不私自改变比较算法、指标方向或 promote 标准。缺少数据时显示“未提供/未校验”，不能由 UI 自动判为不合格或合格。
- **依据/代码**：§2.4、§3.1 证据邻近结论、§3.2、§4.2、§4.8；`App.jsx:6511`、`6838`、`7267`、`7361`。截图 `10-compare-detail-before.png`。

### 4.9 搜索 `/search`、`/search/:id`

- **主信息**：满足明确条件的历史 Run 或研究线集合；主模型为查询与结果集。
- **关联信息**：指标/配置条件、保存视图、搜索范围、命中数。
- **用户动作**：构造条件，查询/重置，清除条件，保存搜索并再次执行。
- **当前骨架**：搜索控制的四个切换按钮 → 已保存视图 → Run 结果 → 研究线结果。当前更接近 API 工具，而不是搜索工作台。
- **具体问题**：未开始查询时标题已叫“已保存 Run 搜索”；默认只见 `limit=20` 而无查询表单；结构化、研究线、JSON、保存视图混为同级动作；两种结果同时显示空表；`Metric / Op / Value` 的 12 列布局不按字段实际宽度分配；输入日期要求手填时间字符串。
- **建议结构**：搜索对象“Run / 研究线” → 常用条件与明确查询/重置 → 命中数和结果表 → 保存视图入口；指标条件作为“字段—运算符—值”一行，配置/JSON 放高级区域；保存操作紧邻当前条件，已用条件始终可见。保留 JSON 高级能力与现有请求内容。
- **依据/代码**：§2.2、§3.5、§4.10–4.11；`App.jsx:6155` SearchPage。截图 `07`、`16`。

### 4.10 研究地图 `/maps`、`/maps/:id` 及内嵌

- **主信息**：列表为地图目录；详情为人工维护的研究命题树、基准路径和选中节点结论。
- **关联信息**：stage 与 decision、绑定 Run 指标、与基准差异、修改原因、来源证据及修订记录。
- **用户动作**：找地图、搜索/定位命题、沿主线追溯、查看证据；WebUI 不修改地图。
- **当前骨架**：列表 + 树画布/右侧总览与节点详情。**树与主从分栏适合该任务**，不建议改成普通卡片墙。
- **具体问题**：当前现场 API 错误与“没有地图”同时出现；列表 catch 后依旧按空数组展示，侧栏错误被吞掉。源码中的去向/阶段过滤实际上将节点变淡，用户可能预期真正隐藏；节点选择、搜索、展开状态未编码进可分享 URL；画布支持节点键盘选择，但 pan/zoom 主要依赖鼠标，需等价入口。宽度上限已在前一轮解除，不重复当成尚未修复的问题。
- **建议结构**：列表标题/范围/搜索 → 地图目录；详情标题与基准简述 → 左树右详情（窄屏上下）→ 详情按“结论—阶段/去向—比较证据—改动/解读/短板/下一步—修订”组织。保留总览；为当前节点提供可复制深链接，区分“筛选高亮”和“只看匹配”；错误、真实空库、无匹配分别表达。
- **依据/代码**：§2.4、§3.5、§4.5、§4.8；`ResearchMap.jsx:112` TreeCanvas、`ResearchMapView`、`ResearchMapList`。参考图 `15-map-user-reference.png` 为用户历史截图，不是本轮实测图；本轮错误态见 `09`。

### 4.11 管理 `/manage`

- **主信息**：陈旧运行、需要复核的研究资产与存储占用；主模型建议为资产巡检队列。
- **关联信息**：项目/研究线/分支归属、最近活动、产物数/字节、统计口径。
- **用户动作**：定位异常资产，打开对象复核；不等于直接停止运行或删除产物。
- **当前骨架**：统计 → 项目压力 → Run/产物排行 → 陈旧运行 → 陈旧研究线。适合资源报表，不利于优先处理。
- **具体问题**：现场显示 41 个运行中、其中 40 个陈旧，但具体陈旧队列在多个排行榜后；“管理”不说明管理对象，“压力”不是超限定义；14 天阈值藏在请求参数，用户无法解释数字。数个两列表格会在常用宽度下各自横滚。
- **建议结构**：标题“研究资产”与巡检口径 → 待复核队列（陈旧运行/研究线）→ 占用分析；进入对象处理，保留现有只读资产统计，不附加清理/取消批量动作。
- **依据/代码**：§2.3 队列、§3.2、§3.5、§4.6；`App.jsx:455` ManagementPage。截图 `08-management-before.png`。

### 4.12 隐藏 Sweep 与跨页创建/编辑/产物视图

- **Sweep**：主信息是参数组合与目标指标，关联 Run 和分支，动作是选择组合/比较；热力图+参数结果表适合，建立在目标和搜索空间明确之上。源码保留列表、summary 等能力，但当前入口关闭；不恢复入口、不改变调度含义。依据 §2.3、§4.2、§4.7；`App.jsx:4098`。
- **创建/编辑**：主信息是当前对象与变更，关联归属/字段约束，动作是校验并提交；短元数据编辑适合弹层，复杂 Run/对比配置若成为高频任务应有可恢复的独立编辑区。当前总“新建”暴露多种后端对象，长表单有原始 JSON，需逐项按现有频率决定，不能一律升级成向导。依据 §4.10–4.12；`CreateModal`、各 `*Form`、`*EditPanel`。
- **产物**：主信息是报告/曲线/表本身，关联来源 Run、版本、单位、样本范围；动作是阅读/比较/下载。保持 Markdown 连续阅读、表格逐字段比较、图表数据替代表达。短预览可弹层，长报告或复杂对照需要独立可分享地址/复用当前原文件入口；不把报告拆成装饰卡片。依据 §2.4、§4.7–4.8、§4.12；`ArtifactDetailModal`、`ArtifactPreview`、`ArtifactComparisonPanel`。
- 上述写入型操作本轮只读源码，不在真实数据上执行；后续用隔离数据验证。

## 6. 仍需用户判断的业务意图

1. **代表结果**：不同页面的默认代表应取最新、最高主指标还是人工指定基准？建议第一批仅显示当前选择依据，保持原算法；地图基准始终用既有指针。
2. **研究线默认任务**：更常见的是读研究地图，还是处理候选评审？影响首屏顺序，不影响功能是否保留。
3. **首页观察范围**：全工作区优先还是当前项目优先？建议保持全局总览，项目页明确局部范围，不让残留面包屑暗示筛选。
4. **比较单位与门槛**：跨资产/不同费用/不同样本窗是否允许直接排优？建议允许已有比较但明示差异；没有统一契约时不新增自动通过/阻断规则。
5. **Run 状态操作的业务含义**：系统记录终态与远程执行器中止是否有额外联动？现有材料不足以认定，先保持 API 行为并精确命名。
6. **地图过滤**：希望“保留上下文、匹配项高亮”，还是“真正隐藏不匹配项”？建议保留现有变淡语义，先改标签并提供清除。
7. **正式验收环境**：当前可访问后端没有可用地图接口，且与象限期权截图不同；地图最终验证需要运行支持地图的现有后端/隔离实例，不能用错误空态替代真实数据验收。

这些是提案中的待决项，不是已经决定改变的产品行为。可以先确认 P0–P2 的页面组织方向，未定语义按上述保守默认保留。
